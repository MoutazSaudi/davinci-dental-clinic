# Appointment management and reminders

Apply migrations with `pnpm db:deploy`, then regenerate the client with `pnpm prisma:generate`.
The schema changes preserve existing notes as administrative/request notes. Clinical notes have a separate field. Existing appointments default to 30 minutes and both reminder consents default to false; do not infer consent from existing contact data.

Only ADMIN accounts can grant permissions or link an account to a doctor from Accounts. The link is unique and optional; no identity is inferred from usernames or client-supplied doctor IDs. ADMIN retains all capabilities. Existing EDITOR accounts with APPOINTMENTS receive shared read access, with no new write or contact permissions. Review and explicitly grant granular permissions after migration. A doctor linked to an account with APPOINTMENTS can view the shared schedule. To edit their own notes/status, grant UPDATE_OWN and STATUS; other doctors' appointments remain protected. A coordinator needs VIEW_ALL, CREATE, UPDATE_ANY, ASSIGN, CANCEL, STATUS, CONTACT and REMIND, plus APPOINTMENTS. Assigning a doctor alone does not grant editing permission.

There is no patient-account model or patient authentication in this repository. Guest requests remain supported; unsupported account/privileged fields are rejected. Public bookings are PENDING until staff confirm. Scheduling uses Asia/Damascus and the existing `geoData.openingHours` from `src/data/seo.ts` (Sunday–Thursday 10:00–20:00, Saturday 10:00–18:00, Friday closed). Staff can adjust the 30-minute default duration. Doctor schedule locks serialize overlap checks. Clinical notes and administrative notes are returned only to authorized appointment editors; patient phone/email and reminder details require CONTACT. Cancellation replaces deletion; appointment events retain status/reschedule and manual reminder history.

## Email setup

1. Set `RESEND_API_KEY` and `RESEND_FROM_EMAIL` to a verified Resend sender. Set a strong random `CRON_SECRET`.
2. Configure the hosting scheduler to call `GET https://YOUR_HOST/api/cron/appointment-reminders` every five minutes (`*/5 * * * *`) with `Authorization: Bearer <CRON_SECRET>`. No hosting scheduler was configured in the repository; automatic scheduling is **not active** just by deploying the endpoint. The endpoint supports Vercel-style authenticated GET requests, or an external/system cron invoking curl. Keep the authorization header in the scheduler's secret store, not source control or logs.
3. Configure a Resend webhook at `https://YOUR_HOST/api/webhooks/resend` for `email.delivered`, `email.bounced`, `email.failed`, and `email.complained`; set its signing secret as `RESEND_WEBHOOK_SECRET`. Use a dedicated Resend configuration for reminders. Unrecognized provider IDs return 503 so an event arriving before the send transaction commits is retried.
4. Send a controlled test to an opted-in test recipient after the migration and scheduler setup. A provider API success records SENT, not DELIVERED. Only a verified delivery webhook records DELIVERED. No actual emails were sent during implementation.

Each confirmed, upcoming, opted-in appointment has one record per channel and reminder revision. Pending reminders are cancelled on cancellation, loss of eligibility, or rescheduling. Rescheduling creates a new revision, preserving prior history. Confirming within 24 hours schedules immediately; the next scheduler invocation processes it. Reconfirming an unchanged appointment or saving unchanged contacts does not generate another email. Reminder emails contain only the appointment time and a neutral rescheduling request.

The worker handles up to 20 due emails per invocation, freezes each request payload, persists an attempt/lease before sending, locks against concurrent appointment mutations during sends, uses a stable Resend idempotency key, and retries up to five times with backoff. Monitor FAILED records and cron HTTP errors. Retry processing stops after 23 hours from the first attempt because [Resend idempotency keys expire after 24 hours](https://resend.com/docs/dashboard/emails/idempotency-keys). This avoids retrying ambiguous sends after provider deduplication expires. Delivery failures with a provider ID are retained for staff follow-up, not automatically resent. [Webhook signatures](https://docs.svix.com/receiving/verifying-payloads/how-manual) use the raw request body, HMAC-SHA256, constant-time comparison and a five-minute timestamp tolerance.

## Manual WhatsApp

The appointments page shows opted-in, confirmed appointments within the next 24 hours that have a valid phone and no successful current email/manual reminder. Local Syrian phone numbers are normalized to +963; other numbers must include an international country code. Opening WhatsApp never updates reminder state. Staff must separately confirm Mark as sent after sending the prepared Arabic message. Repeated Mark as sent requests are idempotent. Authorized staff can open WhatsApp and record a retry from reminder history; each confirmation is audited. A manual SENT record is a staff assertion, not provider-confirmed delivery. No WhatsApp API integration is used.

## Verification

`pnpm test:appointments` runs pure tests for ownership, status transitions, shared validation, phone normalization, timezone boundaries and scheduling.
`pnpm test:appointments:integration` uses the configured **local development** PostgreSQL server, creates an isolated random test schema, applies all migrations there, mocks Resend HTTP responses, and tests API permissions, concurrent bookings/reminders, consent, rescheduling, cancellations and webhooks. It removes only its own random test schema on completion. Never point the integration test at production.
